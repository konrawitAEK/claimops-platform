# สถาปัตยกรรม (ฉบับภาษาไทย)

> ฉบับภาษาอังกฤษคือ [ARCHITECTURE.md](ARCHITECTURE.md) ใช้ส่งกรรมการ ไฟล์นี้มีไว้อ่านเตรียมตัว และมีคำถามที่กรรมการน่าจะถามอยู่ท้ายไฟล์

## ภาพรวม

Spring Boot 3.5 (Java 21) เป็น service เดียว (modular monolith) แบ่งเป็น 3 package:

| Package | หน้าที่ |
|---|---|
| `claim` | ฝั่งเขียนข้อมูล (write model) มี REST API, state machine และ entity ของ JPA เมื่อเคลมเปลี่ยนสถานะจะส่ง event ออกไปทาง Kafka |
| `exposure` | ฝั่งอ่านข้อมูล (read model) รับ event จาก Kafka แล้วอัปเดตยอด `liability_exposures` และ `claim_audit_log` รวมถึงให้ข้อมูล dashboard |
| `common` | ระบุตัวผู้ใช้จาก header, แปลง error เป็น Problem Details, config ของ Kafka และนาฬิกา |

dependency ไปทางเดียว คือ `exposure` เรียก `claim` ได้ แต่ `claim` ไม่รู้จัก `exposure` เลย ฝั่งเขียนจึงไม่ผูกกับฝั่งรายงาน

## สถานะของเคลม

```
SUBMITTED ──▶ IN_REVIEW ──▶ SETTLED
                │  ▲    └──▶ REJECTED
                ▼  │
           INFO_REQUESTED
```

| คำสั่ง | ทำได้จากสถานะ | ไปสถานะ | ใครทำได้ |
|---|---|---|---|
| pickUp (รับงาน) | SUBMITTED | IN_REVIEW | เจ้าหน้าที่คนไหนก็ได้ คนที่กดจะกลายเป็นผู้รับผิดชอบเคลม |
| requestInfo (ขอข้อมูลเพิ่ม) | IN_REVIEW | INFO_REQUESTED | คนที่รับงานเท่านั้น |
| provideInfo (ลูกค้าตอบ) | INFO_REQUESTED | IN_REVIEW | เจ้าของเคลมเท่านั้น |
| settle | IN_REVIEW | SETTLED | คนที่รับงาน ยอดต้องมากกว่า 0 และไม่เกินยอดที่ลูกค้าขอ |
| reject | IN_REVIEW | REJECTED | คนที่รับงาน ต้องใส่เหตุผล |

**จุดที่ test เจอบั๊ก:** ตอนแรกโค้ดเช็กแค่ว่า "ไป IN_REVIEW ได้ไหม" ทำให้เจ้าหน้าที่อีกคนกดรับงานเคลมที่กำลังรอลูกค้าตอบได้ และกลายเป็นคนรับผิดชอบแทนคนเดิม ตอนนี้แก้แล้ว ทุกคำสั่งต้องเริ่มจากสถานะต้นทางที่ระบุไว้เท่านั้น

## ทำไมเลือก REST กับ Kafka แบบนี้

| ช่องทาง | ใช้กับ | เหตุผล |
|---|---|---|
| **REST** | ทุกคำสั่งที่เปลี่ยนสถานะ และการอ่านข้อมูลทั้งหมด | ผู้ใช้ต้องรู้ผลทันที เช่น ได้เลขเคลม หรือได้ 409 ถ้ามีคนรับงานไปก่อน |
| **Kafka** `chubb.claims.events` | อัปเดตยอด exposure และ audit trail | งานต่อเนื่องเหล่านี้ไม่ควรทำให้ request ของเจ้าหน้าที่ช้าหรือล้มตาม ถ้าภายหลังจะเพิ่มระบบแจ้งเตือนหรือตรวจ fraud ก็แค่เพิ่ม consumer ใหม่ ไม่ต้องแก้ฝั่งเขียน |

## เรื่องความถูกต้องของข้อมูล

1. **กันรับงานซ้อน (optimistic locking):**
   - entity `Claim` มี `@Version` ถ้าเจ้าหน้าที่ 2 คนกดรับงานเคลมเดียวกันพร้อมกัน ทั้งคู่อ่านได้ version เดียวกัน
   - คนแรก commit แล้ว version เพิ่มขึ้น คำสั่ง UPDATE ของคนที่สองจึงไม่ตรงแถวไหนเลย ระบบตอบ **409**
   - ที่เลือกวิธีนี้แทนการล็อกแถว (`SELECT FOR UPDATE`) เพราะการชนกันเกิดไม่บ่อย และไม่ต้องล็อกฐานข้อมูลค้างไว้ระหว่างที่ request ยังทำงาน
2. **ส่ง event หลัง commit:**
   - ใช้ `@TransactionalEventListener(AFTER_COMMIT)` ถ้า transaction ถูก rollback จะไม่มี event ออกไป
   - **ช่องโหว่ที่รู้อยู่:** ถ้าระบบล่มหลัง commit แต่ก่อนส่ง event ออกไป event นั้นจะหาย วิธีแก้คือ transactional outbox
3. **ลำดับ event:** ใช้ claim id เป็น key ของ Kafka event ของเคลมเดียวกันจึงอยู่ partition เดียวกัน และถูกประมวลผลตามลำดับ
4. **กันประมวลผล event ซ้ำ (idempotent consumer):**
   - Kafka รับประกันว่าส่งถึงอย่างน้อย 1 ครั้ง (at-least-once) แปลว่า event เดียวกันอาจมาถึงซ้ำได้
   - ก่อนประมวลผล ระบบจะบันทึก `eventId` ลงตาราง `processed_events` ก่อน ถ้ามีอยู่แล้วก็ข้ามไป
   - การบันทึกนี้อยู่ใน transaction เดียวกับการอัปเดตยอด จึงสำเร็จพร้อมกันหรือไม่สำเร็จเลยทั้งคู่
5. **อัปเดตยอดแบบ atomic:** ใช้ `INSERT … ON CONFLICT DO UPDATE` ถ้ามี consumer หลายตัวอัปเดตแถวเดียวกันพร้อมกัน ยอดจะไม่หาย
6. **แยก logic ออกจากการเก็บข้อมูล:**
   - `ExposureProjector` มีแค่กติกาว่า event แต่ละแบบทำอะไรกับยอด
   - การเขียนฐานข้อมูลอยู่ใน `ExposureStore` / `JdbcExposureStore`
   - เพราะแยกกัน จึงเทสต์กติกาได้โดยไม่ต้องมีฐานข้อมูล

**Liability exposure** คือยอดที่ลูกค้าขอเคลม รวมจากเคลมที่ยังไม่ปิด แยกตามประเทศ ประเภท และสกุลเงิน ข้อมูลนี้อัปเดตทีหลังเล็กน้อย (eventually consistent) ส่วนตัวเลขปริมาณงานของทีมอ่านจาก write model โดยตรง จึงตรงทันที

## สกุลเงิน

- เคลมยื่นได้ด้วยสกุลเงินท้องถิ่นของประเทศนั้นหรือ USD ถ้าใส่สกุลเงินของประเทศอื่นจะได้ 422
- ระบบไม่แปลงค่าเงิน ยอดจึงแยกตามสกุลเงินเสมอ เพราะเอา SGD มาบวกกับ JPY ตรง ๆ ไม่ได้ความหมาย

## สิ่งที่ตัดออก (ตอบได้ในช่วง "ถ้ามีเวลามากกว่านี้")

- transactional outbox
- dead-letter topic
- reserve ที่เจ้าหน้าที่ประเมินเอง (ตอนนี้ใช้ยอดที่ลูกค้าขอแทน)
- OAuth2/JWT (ถ้าจะเปลี่ยนมาใช้ แก้แค่ `HeaderAuthInterceptor`)
- integration test ด้วย Testcontainers
- อัปโหลดเอกสาร
- การแปลงค่าเงิน (FX)

## คำถามที่กรรมการน่าจะถาม

- **ทำไมไม่แยกเป็น microservices?** เวลามีแค่ 5 ชั่วโมง ถ้าแยกต้องตั้ง deploy 2 ตัว ฐานข้อมูล 2 ชุด และต้องจัดการ consistency ระหว่างกัน ตอนนี้แต่ละ package ถูกแยกขอบเขตไว้ชัดแล้ว และ `exposure` ไม่อ่านตารางของ `claim` เลย ถ้าจะแยกออกเป็น service ในอนาคต ย้าย package ออกไปได้เลย
- **ถ้า Kafka ล่มจะเกิดอะไร?** ส่วนที่ผู้ใช้เรียก (REST) ยังทำงานได้ปกติ แต่ event ที่ส่งไม่สำเร็จจะหาย เพราะยังไม่มี outbox จุดนี้คือสิ่งแรกที่จะทำต่อ
- **ทำไมใช้ optimistic lock ไม่ใช่ pessimistic?** การชนกันเกิดไม่บ่อย และไม่อยากล็อกแถวค้างไว้ระหว่าง request
- **ทำไมดูเคลมของคนอื่นแล้วได้ 404 ไม่ใช่ 403?** จะได้ไม่บอกว่าเคลมนั้นมีอยู่จริง
